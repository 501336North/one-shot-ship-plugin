- D7 (owner, 2026-11-11, AskUserQuestion, ship round 1): the pen test's deliberate-evasion gaps in the no-Telegram and no-metrics-push keyword guards (lookalike letters, split words, assembled names, an offer that never names Telegram) are accepted as a known limit: logged in FOLLOWUPS as security INFO and listed in the PR body. Careless regressions are covered: both guards now scan every command and skill file (case-insensitive, any file named after Telegram) and the whole repo.
- D8 (owner, 2026-11-11, AskUserQuestion, ship round 5): the pen test's LOW, a test file that SIGSTOPs run_capped's perl parent (or the runner, or any watchdog) hangs the run with no limit, is accepted as a known limit. Every process in the run belongs to the same user, so no in-run fix can close it; only an outer timeout does (Claude Code's 10-minute Bash cap today, a CI job timeout if CI comes back). Logged in FOLLOWUPS and listed in the PR body as LOW.
- D8 CORRECTED (owner, 2026-11-11, AskUserQuestion, after merge, on a heads-up): the reason given for D8 was wrong. Claude Code's 10-minute Bash cap does not apply: preflight and the merge test (`oss-merge-test.sh --v2`) run as background commands with no limit, and the merge test has no overall limit of its own. A branch whose own `npm test` hangs is unbounded too. A hang never merges (READY_TO_MERGE is required); it stalls the ship. Owner chose: plugin 2.1.4 adds an overall time limit to `oss-merge-test.sh` (plugin-owned, so it bounds any hang). A test that deliberately SIGSTOPs the limiter stays a known limit (same user).
- D8 RE-DECIDED (owner, 2026-11-11, AskUserQuestion, same day): no 2.1.4 cap. The hang is LOW: it never merges, it only stalls the ship, and the owner notices and stops it. Kept as a known limit with the corrected reason; the FOLLOWUPS line says so. Radical observability is closed.
