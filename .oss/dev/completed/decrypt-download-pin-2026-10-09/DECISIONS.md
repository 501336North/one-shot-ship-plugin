# Decisions: decrypt-download-pin
- 2026-10-09: Pin to `cli-decrypt-v1.2.3`, not 1.2.1 (MINIMUM_VERSION): 1.2.3 is the first release whose Linux-arm64 binary runs (1.2.2 arm64 crashed, see aarch64-linux-decrypt-support ADR-001). MINIMUM_VERSION stays 1.2.1 (separate concern; not bumped here).
- 2026-10-09: login.md calls the hook instead of its own curl: one downloader, and login gains SHA-256 verification.
- 2026-10-09: Release-side guard via `gh release edit --latest=false` because the SHA-pinned softprops action (v1 @ de2c0eb) has no `make_latest` input.
- 2026-10-09 (Boss: "make sure it adheres to our crypto signing"): binary distribution standard is the oss-launch one — pinned tag + in-release `.sha256` + COMMITTED code-reviewed manifest, fail-closed (code-signing deliberately deferred, see oss-launch-release-hardening DESIGN). Applied to oss-decrypt. Prompt-level Ed25519 manifest signing lives inside the binary and is untouched.
- 2026-10-09: Verify logic mirrored from ensure-oss-launch.sh rather than extracted into a shared lib: session start copies a fixed file list into ~/.oss/hooks, so a new shared file is one more thing that, if not copied, makes every install fail closed. Two copies of ~15 lines, both tested; revisit if a third installer appears.
- 2026-10-09: Release job re-points Latest to the newest cli-decrypt-v* release instead of `--latest=false` on its own release, because demoting without a target leaves GitHub's automatic pick undefined.
- 2026-10-09: "Keep Latest on cli-decrypt" fails the release job loudly if no cli-decrypt-v* release exists (only possible if all are deleted) — intended: a silent no-op would leave Latest on oss-launch.
